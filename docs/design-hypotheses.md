# Astraによる設計仮説

日付: 2026-10-06。原作の静的照合を行ったAstraが提案した設計上の仮説を記録する。原作作者の意図や確認済み仕様とは区別する。採否はADRで決め、以下の推奨だけでコードを変更しない。

| 差分 | どうあるべきかの仮説 | 理由 | 代替案 | 確信度 / 判断 |
| --- | --- | --- | --- | --- |
| F01～F04 | 毎週の貨物を今週の需要から計算し、禁止経路と容量制約を反映する。単価は35～45 | 週次需要・シナリオ指定・原作の処理に対応する | 現状の累積貨物を別の在庫モデルとして明文化する | 高 / 明確な移植漏れの修正候補 |
| F05 | 売却入金と画面見積を数量×価格÷10で統一する | 原作の代金を反映し、見積と実際の入金を一致させる | 単価を先に丸める別の売却規則 | 高 / 明確な移植漏れの修正候補 |
| F07 | 未割当系統のリセットは安全な無操作にする | 設備変更が系統の未設定だけで途中失敗しない | 呼出側がすべて未設定系統を除外する | 高 / 明確な移植漏れの修正候補 |
| F06 / F20 | 割当変更は原子的にし、失敗時は旧運行・余剰数・ダイヤを保持する。同じ編成は余剰＋旧投入数、別編成は新編成の余剰を利用可能数とする | 操作失敗だけで既存運行が消えることを避け、不足数の二重比較も解消する | 明示的な停止操作で旧運行を解除してから割り当てる | 高 / 仕様変更としてユーザー判断が必要 |
| F08 | シナリオの数量は余剰数として維持し、初期投入を減算しない | 原作UIとWPFの項目説明が余剰数を示す。総保有数は余剰＋投入数となる | 総保有数へ再定義して全シナリオを変換する | 高 / 現状維持推奨。投入数の丸めと代入先は別に判断 |
| F09 | 同じ市場の経路追加だけで需要が無制限に増えない設計にする。当面WPFのシェア適用を維持する | 競合の意味と需要の整合性を守る。ただし現在の式が最適とは断定しない | 原作どおり各経路へ全需要、またはOD需要総量を別定義して配分 | 中 / 需要・収益バランスの判断が必要 |
| F10 | ディーゼル自身への投資でディーゼルが進歩する | 無関係な電車投資への依存を避ける | 動力間の技術波及を明文化する | 投資先は高、閾値は中 / WPF維持推奨。閾値変更は別判断 |
| F11 | 設定・表示した目標自身の対象と実際の資金で判定する | 目標と達成条件を一致させる | 原作互換の判定モードを追加する | 高 / WPF維持推奨 |
| F12 | 初期開発と途中開発で同じ技術なら同じ容量にする。閉塞+5、移動閉塞でさらに+5 | 初期化経路だけで技術効果が変わることを避ける | 初期シナリオの容量を独立パラメータ化する | 高 / WPF維持推奨。容量をフラグから算出する改善は後続課題 |
| F15 | 数量コマンドはモデルでも非負に制限する。0は無操作、負数は変更前に拒否する | UI以外からの呼出しでも資産の整合性を保つ | 0も拒否する | 高 / 原作互換とは別の入力契約として判断が必要 |
| F16 | 投入1以上の直接編成にも運行費を課す | 5→6編成の費用段差や系統との違いを避ける | 最初の5編成を明示的に補助し、直接・系統に同じ規則を適用する | 中 / 収支・難易度への影響が大きくユーザー判断が必要 |
| F17 | 累計収支を維持して再建費を追加計上し、規格変更時には旧運行を解除する | 再建で歴史上の赤字を消さず、不適合な車両の継続運行を避ける | 再建後収支を別表示、または適合する運行だけ継続する | 会計と不適合解消は高、全面解除・定着率は中 / 判断が必要 |
| F18 | WPFの廃止時初期化と歴史収支保持を維持する。旧規格の履歴は設備状態と分離する | 廃止後に使える設備と表示履歴を混同しない | 維持費・再開費を定めた休止操作を追加する | 中 / 休止機能を追加するならユーザー判断が必要 |
| F19 / F21 | 見積・支払い・累計収支を同じ計算結果で統一し、待避線と地形を正しく渡す | 会計と見積の整合性を保つ | 原作互換会計を別モード化する | 高 / WPF維持推奨 |

競合案を評価する場合は、同等2経路・逆方向・未運行経路・経路順序変更を比較する。少数編成費用と再建の案は、複数シナリオの収支への影響を確認してから選択する。
