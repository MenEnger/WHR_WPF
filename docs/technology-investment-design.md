# 技術開発の支出履歴と進捗を分離する設計案

日付: 2026-10-06。作成: Astra。**状態: 設計提案・未採用。実装変更を承認するADRではない。**

ユーザーの「投資していないのに累計額が巨額なのはおかしい」という期待から、表示の意味と開発進捗の持ち方を検討した。原作作者の意図は断定しない。今回はこの文書だけを追加し、コード・テスト・既存ADRは変更していない。

## 推奨と期待仕様の仮説

**ゲーム開始後の実支出累計と、初期技術を含む開発進捗を別に保持する案を推奨する。** 初期技術が高くても「開始後の累計投資」は0円から始まる。一方、技術開発の判定は初期技術に対応した進捗を引き継ぎ、既に得た技術をもう一度購入させない。

期待仕様は次の仮説であり、まだユーザーが細部まで指定したものではない。

1. 「累計投資」はプレイヤーがこのゲームで実際に支出した金額を指す。初期技術の換算額は含めない。確信度: 高。
2. 初期技術はシナリオから与えられた能力であり、開始時の資金から再徴収しない。未開発の動力は負の進捗や説明のない進捗を持たない。確信度: 高。
3. 初期設定だけで次週に勝手に技術が上がらず、表示された次の開発費用と実際の完成条件が一致する。確信度: 中～高。既存の初期費用曲線に補正が必要な箇所がある。
4. 開発済み技術の継続費用は、表示を直すだけでは変更しない。新企画などの費用曲線の再設計は別判断とする。確信度: 高。

ここで「投資0では進まない」は**正常な新規開始時の基準進捗**に関する条件である。過去に投資した進捗が十分に残っていて、週ごとの判定回数制限により後の週に完成する挙動まで禁止する意味ではない。

## A案のデータと処理責務

部門別に以下を持つ。名前は実装時に調整する。

- `ActualInvestedSinceStart`: 開始後にその部門へ計上した支出累計。非負のlong。初期技術・補正・無償付与では増えない。
- `InitialResearchCredit`: 開始時の技術状態に対応する基準進捗。非負のlong。資金ではなく、現金へ戻せない。
- `ResearchProgress`: 開発判定用の累積進捗。最初は基準進捗、毎週は実際に計上した投資額だけ増える。完成時には減算しない。
- 技術レベルと新企画フラグ: 獲得済みの能力。従来の車両価格・速度・人口・容量判定は引き続きこちらを見る。

現行の仕組みだけなら`ResearchProgress = InitialResearchCredit + ActualInvestedSinceStart`を導出できる。値を三つ独立に書き換える設計は避け、基準と実支出から導出するか、進捗を保管する場合は等式を常時検証する。将来、研究効率や無償進捗を導入する場合は明示的な別要因を足す。実支出履歴を書き換えて進捗を合わせてはいけない。

週処理では「有効な週次額を確定→資金・週次支出・実支出累計・進捗を同額で更新→既存順序で完成判定」を一組にする。Cは完成閾値と初期換算へ作用し、実支出へ再度掛けない。債務を許す既存の資金処理はこの分離では変えない。「実支出」は現金残高が非負であることではなく、ゲームの資金・支出へ実際に計上されたことを意味する。

現状の通知は投資加算直後、完成判定前に発火する。レベル・次段階・投資停止を同じ画面へ出すなら、完成後にも技術状態通知を送る。最初の履歴分離だけでは既存通知順を不用意に変えず、詳細表示追加時に最終状態を一貫して通知する。

## 初期化とモード再適用

目標の順序は**初期技術の正規化→基準進捗の算出→実支出0→人口など派生値の初期化**とする。

1. モードの技術指定を新しい一時状態へ読む。未指定は新規開始の既定値（蒸気40、他0、新企画なし）を使い、前のゲーム値を参照しない。各週投資も0に戻す。
2. 電気60未満・ディーゼル40未満・リニア300未満を未開発へ正規化し、既存の初期前提補正を適用する。基準進捗は**補正後の最終技術値**から計算する。
3. 新企画は指定された最上位までの既存の前提フラグを導出し、信号技術の容量寄与を再計算する。`+=5`の繰り返しや既存trueの残留を避ける。他の容量要因があるなら技術寄与だけを分離して上書きする。
4. 未開発の動力・新企画なしは基準進捗0。全欄を必ず代入する。開発済みの技術にだけ選択した初期換算ポリシーを適用する。
5. 実支出は全欄0。ここではMoney・週次支出へ技術費を計上しない。技術状態が確定してから既存の人口初期化を行う。

前提補正を「既存と同じ結果にする」ことと「依存関係が満たされるまで何度も適用する」ことは別である。現行は電気→ディーゼル→リニアの順で、後からディーゼル由来で電気100になっても蒸気100補正を再実行しない。最初の対応では**現行の一回適用で得られる技術状態を保持してから進捗を算出**する。依存関係の再帰適用は新たな仕様変更として扱う。

例えば初期電気60により蒸気が40→100へ補正される場合、現行は蒸気進捗625のままだが、補正後に基準を算出すると1373125になる（C=100）。蒸気100という初期能力から次へ進むための整合性は改善するが、継続投資額は減る。これも履歴表示の分離と同じ変更へ紛れ込ませない。

モード再適用を新規開始として技術状態・支出履歴を同じ結果にする。モード適用全体には人口の再乗算や編成追加など別の非冪等な処理もあるため、技術初期化だけの修正を「ゲーム全体の再初期化保証」とは説明しない。通常の新規開始は新しいGameInfoを構成する設計が望ましい。

## 初期進捗・閾値・丸めの設計

初期進捗と完成閾値の式を一か所の計算器へ集め、モデル・見積・画面が共有する。技術状態を変更せずに「次の週に起こる改良」と「そこまでに不足する投資」を計算できる形にする。

最初は既存式をそのまま名前付き関数へ抽出する。次の通常閾値は、レベルをs、係数をCとして蒸気`(s-30)^3 / 5 * C / 4`、電気`(s+10)^3 / 10 * C / 2`、ディーゼル`(s+30)^3 / 10 * C`、開発済みリニア`(s-100)^3 / 20 * C`。未開発電気・ディーゼルには`3000*C`、未開発リニアには`375000*C`の入口判定がある。電気・ディーゼルの入口は通常判定の内側なので、その条件も含めて必要額を計算する。

初期換算の一般形は直前段階の閾値に近いが、厳密な逆関数ではない。現行の動力初期換算をベースにしつつ、正常な開始状態では基準進捗がどの有効な次段階の閾値も越えないように検証する。**360電気の例は移行時に明示的に補正する対象**であり、任意の不正値を全て黙ってclampする設計にはしない。

電気360の補正は、まず基準243135600を高度閾値241885600まで下げる最小修正が可能。厳密`>`なので0投資では進まないが、最小単位の追加投資で進む。高度段階の最初から一定の改良費を払わせるなら、360から高度式を使って基準239385600（350相当）にする案もある。後者は段階間隔として分かりやすいが追加2500001が必要になり、費用バランス変更が大きい。**まずは明示的な最小境界補正を推奨し、後者は別のバランス案に留める。**

計算上の注意:

- 累計の型がlongでも、右辺がint式なら代入前にintで計算される。高度式と新企画式にはこの形がある。大きなCでは中間乗算がオーバーフローし得る。
- 初期通常式は`(long)Math.Pow(...)`の後に整数除算する。一方、週次通常閾値は`Math.Pow`由来のdouble式で、途中の除算を整数として切り捨てない。floatではなくdoubleである。
- C=100・電気60の初期値は`floor(65^3/10)*100/2=1373100`。途中切捨てを省いた1373125とは25単位違う。式を見た目でまとめると既存費用が変わる。
- 最初の抽出では型・括弧・演算順・比較を保持する。long化や有理数化は別差分で、通常域の結果一致と既存オーバーフロー域の意図した変化を確認する。新設計では最初の乗算からchecked long、必要なら厳密な有理数で定義し、受理するC・技術値の上限も明文化する。
- 金額単位を1円に変更しない。累計が整数で厳密`>`なら最小到達値は`floor(閾値)+1`、`>=`なら`ceil(閾値)`。残額はそれと進捗との差の非負部分。double式の互換検証なしで全閾値を単純整数除算へ統一しない。
- `TechCost`はロード時に1未満を100へ補正するが、モデルのpublic値には別途制限がない。計算器は有効Cを前提とし、不正Cは設定境界で拒否する。進行中のC変更は初期基準の意味も変えるため、当面シナリオ固定値とする。

## 高度段階・完成後・投資不可の扱い

高度ディーゼルはADR0005どおりディーゼル自身の進捗だけを見る。電車への投資でディーゼル進捗を加算せず、電気技術を高度判定の条件に追加しない。

現行では通常+5の後に高度+10を判定する。電気は通常の355→360から高度へ進める週があり、ディーゼルは360以降も通常+5と高度+10が同週に併存する。後続閾値は**先の改良後のレベル**から計算する。次改良表示は単一の直線的な進捗バーを先に作るより、「次週に見込まれる改良」と条件別の残額を同じ順序で試算する方が正確。実装段階では通常改良と高度改良を一つの排他的な分岐へ書き換えない。

あるべき完成後の契約は「履歴は残す、完成した部門へ新たに課金しない、能力上限を越えない」と考える。ただし現行モデルには上限の一律ガードがなく、停止条件が`==150/360/990`なので、同週の複数改良や不適切な初期値で上限を飛び越す経路がある。**履歴分離だけの段階ではここを一緒に変えず、上限・自動停止のモデル契約を別途承認してから実装する。** 360は最終完成ではなく従来の投資自動停止点なので、勝手に最終完了扱いにしない。

同様に通常投資UIの条件（電気は蒸気80、ディーゼルは電気80、リニアは電気またはディーゼル200、蒸気の年代制限）は今回の高度独立とは別である。現行ではUIの投資選択可否とモデルの課金・改良判定が一致しない。推奨する最終形は、投資開始可否・継続課金可否・蓄積済み進捗による改良可否を明示的に分ける設計だが、各前提を存続させるかはこの文書で決定しない。画面には投資不可の理由を示し、モデル側の統一は別段階とする。

## 新企画は費用再設計を分ける

新企画なしは初期基準0へ必ず代入する。開発済みの場合はフラグを能力の正として扱い、実支出0と両立させる。

現行の初期新企画基準は週次の完成閾値と一致しない。閉塞信号なら初期`1000*C/20`に対し完成閾値`1000*C`。デュアルシートは初期`100000*C/20`に対し完成閾値`200000*C`であり、単なる全項目20倍の修正にもならない。初期フリーゲージ・移動閉塞でも初期係数と対応する完成段階の係数が違う。

最初は**旧初期基準を互換用のResearchCreditとして維持**し、開始後の実支出だけを0と表示する。これで次の未開発技術までの既存費用を維持できる。UIが「取得済みならこの閾値までは支払済み」と推定してはいけない。

将来の整合案は、獲得済み最上位技術の完成閾値そのものを初期基準にすること。閉塞のみ・C=100なら、旧5000から100000へ変更し、次の転換クロスまでの残額は495000から400000になる。説明しやすい設計なので長期的には推奨するが、開発を早め、後の人口・運行容量・費用へ波及する。**今回の表示改善には含めず、各モードの次段階費用を比較してから採否を決める。**

## UI案

主表示は「部門 / 週次投資 / 開始後の累計投資」。新規開始時には全欄0円となる。初期技術が高い場合も同じで、補足に「初期技術は累計支出に含みません」と表示する。

詳細には「現在の開発可能速度」「未開発 / 改良可能 / 完成」「次の改良までの追加投資」を出す。高度段階は価格低減と速度上限に作用する現状を正しく説明する。初期ResearchCreditの巨額を主画面へ再表示する必要はない。必要なら詳細の「初期技術による進捗」に限定し、実支出と明確に区別する。

例: 初期電気60なら「開発可能速度60km/h、開始後の累計投資0円」。2000万円を1週計上したら累計2000万円になり、基準進捗は変えず判定用進捗を200単位増やす。設定しただけで週を送っていない間は累計0円のまま。

進捗率や残り週数を出すなら、丸め・同週複数改良・0投資・投資不可を含めてモデルの試算結果を使う。0投資での残り週数を除算で求めず「投資なし」、既存蓄積で次週に完成できる場合は「次週判定で改良見込み」とする。週次額は変更できるため、週数は目安と明示する。

金額書式の絶対値化は原因の一部だが、全画面の符号を変えるのは独立した表示修正。投資履歴はモデルで非負を保証し、負値を絶対値にして正常値へ見せかけない。書式関数を共用する際には円への乗算オーバーフローも含めて扱う。現状の300×280固定画面へ列を詰め込まず、詳細部または画面幅を調整し、長い金額と日本語の実表示を確認する。

## 影響と変更しない条件

表示分離だけなら週次資金・費用・完成週・技術値・車両価格・人口倍率を同一に保てる。技術の基準進捗を補正すると完成週が変わり、その後に車両価格、開発可能速度、技術目標、人口、運行容量、運行費へ波及し得る。`GameInfoPopulation.cs:11–26`は技術レベルとフラグを見るので、履歴変数だけを分離しても人口式自体を変える理由はない。

今回の提案でそのまま維持するもの:

- 動力・新企画の既存週次閾値、比較の厳密性、判定順、週ごとの改良回数。
- ADR0005の高度ディーゼル独立、通常+5と高度+10の併存、360の従来自動停止。
- 原作比較で保留中の競合、運行費、初期編成、通常開発UIの前提など。
- 支出後の負債を許す現行処理、金額単位、Cの作用、既存の人口計算式。
- 新企画の初期`/20`等は履歴分離・初期化修正段階では互換基準として保持する。

既存セーブ・ロードは`ApplicationUtil.cs:66–98`で無効化されているので、今回それを復活させない。将来旧状態を移行するなら、旧累計から技術レベルだけを見て実支出を正確に逆算することはできない。初期モード・旧計算バージョンが確定しなければ「過去の実支出不明」とし、移行後から記録する。架空の履歴を作らない。

## レビュー可能な移行手順

1. **履歴分離**: 既存AccumulatedInvestを開発進捗として扱い、新しい開始後実支出を追加。表示を新履歴へ切り替える。旧進捗初期値・閾値・技術状態はこの段階ではそのままなので、実支出0表示以外の結果一致を確認できる。負の旧進捗や電気360の問題は「未解消」と明記する。
2. **計算器抽出**: 旧初期値・閾値・次週改良の試算を副作用なしにする。型と丸めを維持したまま境界テストを作る。詳細UIはこの試算を共有する。
3. **新規開始の整合**: 未開発0、最終技術から基準算出、全項目の上書き、モード再適用残留防止、0投資で進まない電気360の明示補正を採用候補にする。旧値との差と次の開発費用を一覧にしてレビューし、承認後に実装する。
4. **独立した後続判断**: 新企画の初期基準統一、算術の型・丸め統一、最終上限・完成後課金防止、通常前提のUI/モデル統一。前段が終わったことを理由に自動採用しない。

段階1の旧進捗を保ったまま実支出だけを分離する実装では、旧進捗を暫定保管し、まだ非負のInitialResearchCreditと呼ばない。段階3で正常化した新規開始から基準＋実支出という不変条件へ移る。これにより負値を有効な新設計の値として固定しない。

## 採用前に絞って確認したいこと

1. **累計表示の意味**: 「このゲーム開始後の実支出」にし、初期技術を別表示するA案を採用するか。ユーザーの期待に最も合うと考えるが、初期技術込みの相当額を見たい場合はB案も成立する。
2. **今回進める範囲**: まず履歴分離までか、別レビューを挟んで未開発0・初期補正後の基準・残留防止・電気360の最小補正まで進めるか。後者には継続費用の変更があるため、具体的な差を示してから採用判断する。

新企画の基準統一や通常投資前提・最終上限は、上の二点の回答に混ぜず、後続の個別判断として残す。
