# ADR 0028: 車両・編成の新規作成で入力契約違反を拒否する

日付: 2026-10-08
状態: 採用（ユーザー判断）。仕様・影響と設計を別々にAstraレビュー済み。

## 背景とユーザー判断

ADR 0025は編成作成登録を挙動維持で本体へ移したが、負速度・負数量・未定義enum・ゲーム未登録Carを受理する経路が残っていた。数量ボタンの上限は1車種16両だが、本体には適用されていなかった。

現状、選択肢、拒否の互換性への影響、シナリオ初期編成の別経路を説明した。ユーザーは、未定義enumを使う意図がないことと、他の入力も本体で拒否して契約を検証する方針を回答した。

## 決定と理由

- 車両開発は負速度と動力・軌間・座席・車体傾斜の未定義enumを拒否する。
- 編成作成は負数量、1車種16両を超える数量、選択Carの負速度と上記enum・軌道タイプの未定義値を拒否する。数量0は未選択であり、車両属性検査の対象外とする。異なる車種の合計16両超は許可する。
- GameInfoの編成操作は選択Carがそのゲームのvehiclesに参照として含まれることも要求する。Factory単体はゲームに依存しない数量・属性・組合せ検査を担当する。
- 照会と実行で同じ検査を行う。拒否は構造化した理由・要求値で返し、支払・登録・既存在庫・通知を変更しない。内部例外の一括変換は行わない。
- 検査した構成と登録する構成を一致させる。ADR 0025の検査後再列挙の維持は、この新規則の追加に限り、一度列挙した入力から検査・生成する方式へ変更する。入力列挙前の登録先取得は維持する。
- UIの拒否表示・実行可否・実行前検査は本体へ揃え、不正入力の見積を先に計算しない。確認承認後にも本体が再検査する。

理由は、画面や将来のハーネスを経由してもゲーム本体が同じ入力契約を守り、未知の種類や不適切な数量を登録しないためである。

## 操作API方式

ユーザーは既存の検査・実行メソッド方式で進めることを選択した。今回の契約はこの方式でも守れるため、Command型・型別Executeの導入を同じ変更へ混ぜない。入力をまとめるCommand方式は[Issue #60](https://github.com/MenEnger/WHR_WPF/issues/60)で、利点・重複・評価順の互換性を別途検討する。

## 範囲と互換性

シナリオ初期DefautltCompositionは新規作成と別経路であり、今回の制限を読込へ適用しない。既存編成の削除・補正や、開発済み車両の常時監視も行わない。定義済みenumには既存技術条件を適用し、新しい組合せ制限は加えない。SeatEnum.Noneは1であり、0も未定義値として扱う。

これまで受理された呼出しには拒否が追加される。独自Carを使う呼出元は先にゲームへ登録し、未選択の数量は0を使う必要がある。17両以上の新規作成はできなくなる。公開モデルの変更や並行操作の原子性は保証しない。

速度0・蒸気技術0の除算、算術overflow、投資額・運行等の他enum、モード開始の契約は対象外。費用計算・速度計算の低水準APIには業務検査を重複追加せず、今回の作成・UI見積境界で検査する。

## 代替案

- 現状維持：互換性は高いが、画面外の入力が契約をすり抜ける。
- UIだけで拒否：別UIやハーネスが同じ規則を再実装する必要がある。
- 16両上限をUIだけに残す：検討したが、他の入力も本体で拒否するユーザー判断に従い、今回は新規作成の契約に含める。
- シナリオ読込や全計算APIにも一括適用：既存初期編成の受理や他操作へ波及するため対象外とする。

具体的な優先順位、UI見積、設計と検証は[設計文書](../design/creation-input-contract.md)に記録する。
