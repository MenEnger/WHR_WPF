# ADR 0025: 編成の作成とゲームへの登録を本体操作にする

日付: 2026-10-08
状態: 採用。仕様・影響、設計を別々にAstraレビュー済み。

## 背景

ADR 0006 / Issue #28の共通操作調査で、編成の検査/生成はUI非依存Factoryにあるが、ゲームへの登録だけVMが公開リストへ直接追加していると確認した。画面なしで作成を完了する操作が本体に不足している。

## 決定と理由

GameInfo.CreateCompositionは、既存Factoryによる検査/生成と、そのゲームへの登録を一つの本体操作として提供し、登録した同一Compositionを返す。UIの確認後処理をこの操作へ接続する。見積/CanExecute/表示は既存処理を保つ。

旧式compositions.Add(Factory.CreateComposition(...))と同じく登録先を先に取得し、Factory成功後に一度だけ追加する。Factoryの再列挙・理由優先順位・内部例外、作成だけでは資金/余剰数を変更しない挙動を維持する。失敗は既存拒否例外か内部例外のまま伝播し、一般例外を拒否へ一括変換しない。登録失敗の巻戻しを新しく保証しない。

## 代替案

- VMで直接登録を続ける：本体操作がゲームへの登録まで担えず、他のUI/ハーネスに同じ処理が必要になる。
- 全操作facade/共通コマンド/新結果型を追加する：既存APIで実行できる操作が多く、この不足の解消には過剰。
- Factoryの入力snapshotや新入力規則を同時追加する：再列挙や未検査入力の意味を変える。責務移動と分け、判断待ちを解消した操作ごとに扱う。

## 影響と検証

公開APIは追加のみ。Factory・公開モデルの互換性は維持し、Core/Scenario/UIの依存はADR 0024のまま。今回だけで#28の全操作/入力検証完了とはしない。負数量/enum/所属/16両上限などはpending-decisions.md、既知候補はbug-notes.mdに残す。

正常登録の同一性/一回、既存拒否、内部例外、登録先の評価順をCoreで検査し、WPFでVM確認後コールバックの接続を検査する。Factoryの各条件は既存テストを再利用する。検証結果は[実装文書](../design/composition-registration-operation.md)へ記録する。
