# ADR 0006: UIを差し替えられるゲーム本体と共通の操作窓口

日付: 2026-10-06
状態: 採用（ユーザー判断）。実装は未着手。

## 背景

ユーザーは操作しにくい部分を含め、UIを大幅にモダン化したい。将来のWeb対応やシナリオ形式の再検討も見据える。画面の変更がゲームルールや状態の整合を壊さない構造と、変更を検出するハーネスが必要である。

既存の混入箇所は[UI境界調査](../ui-boundary-audit.md)に記録した。ユーザーが合意した到達点は「UIを差し替えてもロジックは動く」「画面なしで一通り遊べる」である。

## 決定

- 同じリポジトリ・ソリューション内にUI非依存のゲーム本体を置く。WPF・将来のWeb UI・テスト用ハーネスは同じ本体と操作窓口を利用する。
- 本体はシナリオ開始、建設・改造・休止・再建、技術投資、車両・編成作成と売買、路線・系統の運行設定、週送り、目標判定などのゲーム操作と入力検証を担当する。検証をUIだけに置かない。
- 操作の入力、見積、適用可否、拒否理由、結果、状態とイベントを構造化する。UIやハーネスが私有フィールドの書換えで操作を再現する構造を避ける。操作窓口の具体的な型と粒度は実装時に決める。
- 本体はWindow、画像オブジェクト、ダイアログ、アプリ終了、画面専用の表示文言・整形に依存しない。確認・表示・文言はUI側で担当する。
- 旧・新シナリオ形式の読み込みは共通のシナリオデータへ変換し、本体へ渡す。新形式や途中セーブの形式、バージョン・移行方針は別途設計する。シナリオと途中セーブの役割を区別する。
- 現状挙動のテストを整えながら段階的に分離する。分離と数式・費用・割当・期限の仕様変更を混ぜない。既知の不具合は別の変更で扱う。

駅名・利用者が付けた車両名・シナリオ作者の説明文はデータとして本体に持てる。INotifyPropertyChangedや診断例外を機械的に排除する決定ではない。

## 完了基準と検証

1. WPFを起動せず、共通の操作窓口だけでシナリオ開始から主要な建設・投資・売買・運行設定・週送り・目標達成まで実行できる。終了理由や拒否も画面なしで取得できる。
2. 乱数を含む入力を統制し、同じシナリオと操作列から同じ状態・イベントを再現できる。画面のダイアログや日本語の通知文を検査する必要がない。
3. 資金と帳簿、編成保有と投入・返却、路線と系統の参照、休止状態などの整合を検証する。失敗時の状態保持は、現状記録と採用済み仕様を区別する。
4. 本体と操作窓口のテスト、UIの主要操作経路のテストを分ける。UIテストは選択、入力、見積、確認、取消、表示更新を守り、画面位置や文言の過剰な固定で再設計を妨げない。
5. 本体からUIへの逆向き依存をプロジェクト参照で防ぐ。UIを使わないビルド・テストで本体を検証できる。

「画面なしで一通り遊べる」は実装済み機能のゲーム操作を指す。未実装機能一覧の全件を完成させることや、Web版を公開することを分離完了の必須条件にはしない。

画面なしの完了確認は、以下の既存操作へ対応づける。ハーネスの完了条件だけで新たなゲーム仕様を決めない。

| 操作 | 確認対象 |
| --- | --- |
| シナリオ開始 | 共通データから難易度・モードを適用し、初期状態を取得する。 |
| 路線建設・改造 | 見積、可否、建設、速度・軌間・電化・線数・待避線の変更。 |
| 路線休止・再建 | 設備保持、運行解除と返却、再建費用と再設定。 |
| 技術投資 | 部門別週次額の設定、開発判定と停止、構造化した通知。 |
| 車両・編成作成 | 設備・技術の適合、作成可否と費用、作成結果。 |
| 編成売買 | 数量と資金の検証、購入・売却と余剰数の変更。 |
| 路線・系統の運行設定 | 編成・本数・ダイヤ、見積と割当・解除、状態整合。 |
| 週送り | 収支・需要・人口・経済・年越し・戦時・開発の状態と通知。 |
| 目標判定と終了 | 達成・フリーモード移行、未達期限切れ、終了理由の取得。 |

それぞれ、正常系だけでなく、入力拒否・費用不足・実行不可などその操作に該当する境界を確認する。失敗時の状態保持は採用済み仕様または現状記録に基づいて検査する。

## 未決事項

- Webで本体を動かす場所（ブラウザ内・サーバー等）と通信方式。今回の決定はWeb実装方式を固定しない。
- UIのフレームワーク、画面設計、操作窓口のAPI形式。
- 新シナリオ形式・保存形式の具体的な形式、移行方法。
- 想定内の操作拒否、内部診断、ゲーム終了を表す型と、部分失敗時の適用範囲。既存の不具合を新設計の契約として自動採用しない。
